# v0.11 — token-budget-aware prompt assembly (M3)

Branch `claude/v0.11-token-budget-prompt` (base `135c31a`). Independent of the parked v0.13 SSE branch.

## §0 一句话

在 `_open_turn` 组装 prompt 时，按 `(provider, chat_model) -> context_window` 减去 completion 预留得到 budget；若 `prefix + suffix` 估算超 budget，按低分→高分**整片 drop** retrieved slices（prefix / user query 永不动），把"丢了哪几片"写进 trace 事件。

## §1 物理硬墙 + spike 笔记

三条候选 spike，全部 30 分钟内自查可决：

1. **char/4 启发式在中英混合上的误差** — 不 spike。`mneme/llm/client.py:161` 已有 `est_tokens=payload_chars // 4` 的内部精度先例，v0.11 沿用即可；本版裁剪策略是"整片 drop"而非"卡 byte 末位"，误差 ±15% 不会把"刚好放下"变成"放不下"——只是多 drop 0~1 片。v0.12 真撞上"该留没留"才升级。
2. **per-model 维度** — 不 spike。三家上下文窗口在主流 chat 模型上分散度大（gpt-4o 128K / gpt-4o-mini 128K / claude-sonnet-4-6 200K / claude-haiku-4-5 200K / deepseek-chat 64K / ollama 默认 8K~32K 不等），必须按 `(provider, chat_model)` 查表。结论：直接做。
3. **三段分别计算 tokens (system / tools schema / messages)** — 不 spike。本版调用 `assemble_prompt(prefix, slices, suffix, budget)` 仅传入 prefix+suffix；tools schema 的 token 算入"固定开销"统一从 budget 里扣（见 §3 `_TOOLS_SCHEMA_RESERVE`，pin 1024）。够用。

物理硬墙清单（design-time pin，不查证不写代码）：

| Provider | Model | context_window (tokens) |
|---|---|---|
| openai | gpt-4o | 128000 |
| openai | gpt-4o-mini | 128000 |
| anthropic | claude-sonnet-4-6 | 200000 |
| anthropic | claude-haiku-4-5 | 200000 |
| deepseek | deepseek-chat | 64000 |
| ollama | * (任意) | 8192 |

Ollama 选 8192 是 qwen2.5:7b 等常见模型的默认 `num_ctx`；用户改 modelfile 后我们查不到，因此 ollama 一律返回**保守值**（PRINCIPLE 3 stdlib 优先 + 4 本地默认）。

## §2 token 计数公式 pin（Unit A）

```
estimate_tokens(text: str) -> int
    return len(text) // 4 + 1
```

理由：与 `client.py:161` 既有 `_audit("...", payload_chars // 4)` 字面一致 → 单一公式，**不**为 EN/CN 写不同分支（PRINCIPLE 1）。`+ 1` 把空串映到 1，避免 budget 算术里 0 干扰（"空 suffix" 仍占一个 token 位）。

公式不区分 model（unit A 是 pure str→int，PRINCIPLE 1）；CN 偏低估、EN 偏准——结合 §3 `_COMPLETION_RESERVE_RATIO=0.25` 的 25% 预留，足以兜住误差。

**字面 pin**：函数名 `estimate_tokens`，签名 `(text: str) -> int`，公式 `len(text) // 4 + 1`，模块路径 `mneme/llm/budget.py`（新文件，整个 M3 的 token 工具集中此）。

## §3 context window 数据源 + lookup pin（Unit B）

**数据源**：`mneme/llm/pricing.yaml` 顶层新增 `context_windows:` 段，与现有 `openai: / anthropic: / deepseek:` 平级**不冲突**（pricing.py 只读 provider keys；新段加新 loader）。

```yaml
context_windows:
  openai:
    gpt-4o: 128000
    gpt-4o-mini: 128000
  anthropic:
    claude-sonnet-4-6: 200000
    claude-haiku-4-5: 200000
  deepseek:
    deepseek-chat: 64000
  ollama:
    "*": 8192
```

放 `pricing.yaml` 而非新文件：PRINCIPLE 1 "不引新实体"——这俩表更新节奏一致（厂商发模型时同时给价格和窗口），合并降低维护税。

**lookup pin**（Unit B，pure）：

```
context_window_for(provider: str, model: str) -> int
```

- `provider == "ollama"` → 直接返回 `context_windows.ollama["*"]`，**不**按 model 细查（用户的 modelfile num_ctx 我们查不到，统一保守 → silent，无 warning）。
- 表内命中 → 返回 int。
- 表内未命中（unknown provider / unknown model 在云上）→ **silent 返回 fallback `8192`**，并 stderr 一行 `mneme: unknown context window for {provider}/{model}, falling back to 8192 tokens` —— 与 pricing.py 一次性 stderr 风格一致（PRINCIPLE 1 复用、PRINCIPLE 5 可观察）。一个 (provider, model) 仅 warn 一次，靠 module-level `_warned: set[tuple[str, str]]` 实现。
- yaml 解析失败（`context_windows:` 段缺失/不是 dict）→ 同样 fallback 8192 + 一次性 stderr `mneme: pricing.yaml missing context_windows section, falling back to 8192 tokens`。

**budget 公式**（也在 Unit B 里 pin，pure）：

```
budget_for_retrieval(provider: str, model: str) -> int
    window = context_window_for(provider, model)
    completion_reserve = max(1024, window // 4)        # 25% or floor 1024
    tools_schema_reserve = 1024                         # constant
    return max(0, window - completion_reserve - tools_schema_reserve)
```

字面 pin：`_COMPLETION_RESERVE_RATIO = 4` (整数除法，即 25%)，`_COMPLETION_RESERVE_FLOOR = 1024`，`_TOOLS_SCHEMA_RESERVE = 1024`，`_FALLBACK_WINDOW = 8192`。所有值在 `mneme/llm/budget.py` 顶部模块常量。

**用户暴露面**：单一 env var `MNEME_CONTEXT_BUDGET_RATIO`（见 §8）覆盖 25% 那一项；其他常量不暴露（PRINCIPLE 1，少一个开关 = 少一种 bug）。

## §4 assemble_prompt 算法 + drop 策略 + 失败模式 pin（Unit C）

```
assemble_prompt(prefix: str,
                slices: list[Slice],
                user_text: str,
                budget: int) -> tuple[str, str, AssemblyMeta]
```

返回 `(prefix, suffix, meta)`，签名沿用 `agent.build_prompt` 的 `(prefix, suffix)` 二元组以最小改动接入 `_open_turn`。`meta` 是新 dataclass：

```
@dataclass(frozen=True)
class AssemblyMeta:
    estimated_tokens: int        # prefix + suffix 估算后的总 token
    kept_slice_ids: list[str]    # 顺序与 suffix 中出现顺序一致
    dropped_slice_ids: list[str] # 被 drop 的 slice id，list（保顺序，便于复现）
    original_slice_count: int    # len(slices) 入参时
```

**算法**（pure，pin 步骤顺序）：

1. 调 `build_prompt(user_text, slices, blueprint)` 得初版 `(prefix, suffix)`，估算 `t = estimate_tokens(prefix) + estimate_tokens(suffix)`。
2. `t <= budget` → 直接返回，`dropped_slice_ids = []`。
3. `t > budget`：进入 drop 循环。**drop 顺序 = 按 slice 在 `slices` 中的位置末尾向前**（retrieve.py 已按 score DESC, id ASC 排好，末尾分最低）——每次弹掉一个 slice，用 `build_prompt(user_text, kept_slices, blueprint)` 重新构造 suffix，重估 token。
4. 循环退出条件：
   - `t <= budget` → 返回（kept_slice_ids = 剩余 slice ids，dropped_slice_ids = 已 drop ids）。
   - `kept_slices == []` 仍 `t > budget`（说明 prefix + 空-slice suffix + user_text 仍超 budget）→ **raise `PromptTooBig`**（见下）。

**为何重建 suffix 而不只减字符**：保 `build_prompt` 单一来源——recall yaml 的 `slice_line` / `empty` 模板才决定 suffix 形态，避免双写 (PRINCIPLE 1)。重建是 O(n_slices²) 但 retrieve 最多返 ~10 片，可忽略。

**失败模式 pin**：

| 情形 | 行为 | 字面值 |
|---|---|---|
| 估算超 budget，drop 后入 budget | silent return，meta 含 dropped | — |
| 估算入 budget（不进循环） | silent return，dropped_slice_ids=[] | — |
| 所有 slice drop 完仍超 budget | **raise `PromptTooBig`** | `f"prompt exceeds budget after dropping all {n} retrieved slices: estimated={t} budget={budget}"` |
| budget <= 0（context_window 损坏） | 同上 raise（不静默吞，因为是配置错） | 同上字符串 |
| slices=[] 入参 + 估算超 budget | 直接 raise（无 slice 可 drop） | 同上 |
| **预测超 budget 但实际 LLM 端真 token < provider 限** | silent（我们已 drop，不能撤）— design accepts 偶发"过度裁剪"作为启发式代价 | — |

`PromptTooBig(Exception)` 类放 `mneme/llm/budget.py`，字段 `estimated: int`, `budget: int`, `dropped_count: int`。

## §5 agent.py 集成点（Unit D）

仅改 `_open_turn`：build_prompt 之后插入 `assemble_prompt`，把 meta 透出到 trace。

伪 diff：

```
slices = retrieve.recall(...)
prefix, suffix, meta = budget.assemble_prompt(
    prefix=..., slices=slices, user_text=user_text,
    budget=budget.budget_for_retrieval(provider, model),
)
# build trace as before, plus:
prompt_assembled_tokens=meta.estimated_tokens,
prompt_dropped_slice_ids=meta.dropped_slice_ids,
# used_slices = meta.kept_slice_ids (注意：v0.10 之前 used_slices = [s.id for s in slices]
#  现在用 kept_slice_ids — 见 §7 兼容性)
```

`assemble_prompt` raise `PromptTooBig` 时：`_open_turn` **不**捕获，让 raise 冒到 `respond()` / `respond_stream()` 的 caller（CLI / HTTP server）。CLI 端 v0.11 不动 catch（用户看见 traceback，是设计目标——这是"user query 本身太长"，需要人工干预）；HTTP server 同样不 catch（500，可见性同 v0.10 其他异常）。

**为何不 fallback 截 user_text**：PRINCIPLE 5 可解释 + 用户的 query 是 ground truth，悄悄截会让 reply 答非所问，比 raise 更糟。

**`_open_turn` 写 trace 顺序**：仍是"先写 open trace，再 LLM 调用"。`assemble_prompt` raise 时 trace 已写——但此时 `used_slices` 未定。决策：**raise 路径不写 open trace**（移动 events.append 到 assemble 之后），与"crash before LLM 仍留痕"的原 v0.7 意图轻微相悖，但此处 raise 不是 LLM 失败而是 input 失败，trace 没意义；append 改顺序的代价是若 assemble 之后到 events.append 之前崩了无痕——可接受（events.append 本身极简）。

## §6 events.jsonl 新字段 / 新 kind（Unit E）

**不新增 kind**，复用已存在的 `kind="trace"` open-trace 行，仅追加字段：

| 字段 | 类型 | 何时写 | 含义 |
|---|---|---|---|
| `prompt_assembled_tokens` | int | 总是（open trace） | `meta.estimated_tokens`（启发式） |
| `prompt_dropped_slice_ids` | list[str] | 总是（open trace），空 list 也写 | 被裁剪掉的 slice id 列表，保 drop 顺序 |
| `used_slices` | list[str] | 总是（open trace），**语义改变** | 现在 = kept_slice_ids（实际进 prompt 的），不再是 retrieve 返回的全集 |

**为何不新 kind**：PRINCIPLE 1 + 一次 LLM 调用对应一组 open/close trace，足够表达；新 `kind="prompt_trim"` 会要求 explain() 多 join 一个 source（复杂度税）。

**字面值 pin**：
- 字段名严格 `prompt_assembled_tokens` / `prompt_dropped_slice_ids`（**复数 ids**，与现有 `used_slices` 复数风格一致）。
- 空 dropped 时写 `"prompt_dropped_slice_ids": []`，**不省略**——下游 stats 解析时存在性保证。
- `prompt_assembled_tokens` 是启发式估算，不是真 token；命名故意带 `assembled` 与 close-trace 的真 `prompt_tokens`（来自 provider usage）区分。

**explain() 不改**：现有 merge-by-id 自然把新字段合进 dict。

## §7 v0.7-v0.10 兼容性矩阵

| 关注点 | v0.10 行为 | v0.11 行为 | 影响 |
|---|---|---|---|
| `build_prompt(user, slices, blueprint)` 公开签名 | 不变 | 不变（保留，assemble_prompt 内调用它） | 0 |
| `prompt_hash` 输入 | `prefix + "\n" + suffix` | 同公式，但 suffix 在裁剪后 slices 减少 → hash 改变 | **真代价，见下** |
| `prompt_hash` 在 slices=[]（任何理由）时 | 一个值 | 同一个值（drop 到空也产生相同 suffix）—— 但若 raise 则不会写 hash | session 测试不受影响（同 session 内 retrieve 仍稳定） |
| `used_slices` 字段语义 | retrieve.recall 返回的全部 | **kept_slice_ids** | 测试需调整：`test_session.py:R-19` 等只比对 hash 不读 used_slices 的，不影响；任何 `assert used_slices == [...]` 显式列出全集的会 break |
| `_open_turn` trace 写入位置 | retrieve 之后立刻写 | assemble 之后写（raise 路径不写） | 边缘崩溃场景痕迹略减，但 raise 类型仅 `PromptTooBig`（输入问题，不是 LLM/IO 失败） |
| Ollama / cloud 短 prompt | 不动 | budget 远大于估算，等价不动 | 0 行为变化 |
| `test_session.py:R-19 prompt_hash 跨 session 一致` | pass | pass（session_id 仍不入 hash） | 0 |
| `test_agent.py test_build_prompt_keeps_retrieval_out_of_the_prefix` | pass | pass（assemble_prompt 仍把 slices 进 suffix） | 0 |
| HTTP `/chat` cost / session 行为 | 不变 | 不变（新字段对响应体不可见） | 0 |
| v0.7 daily token budget | 不变 | 不变（独立机制，与 context budget 无耦合） | 0 |

**prompt_hash 改变的影响域**：仅"超 budget 触发 drop"的真实大 prompt 场景。短 prompt（绝大多数本地开发 + 测试 fixture）等价行为，hash 不变 → provider 端 prompt cache 命中率不退化。PRINCIPLE 2 代价已最小化到"该退化时才退化"。

**v0.10 测试需调整清单**（移交 dev 时点名）：
- 无显式列举 `used_slices` 全集的断言 → 全部直接通过。
- 若 dev 找到 `assert "used_slices" in record` 这类存在性断言：通过。
- 若发现 `assert record["used_slices"] == [...]` 全量等价：需在 v0.11 的 test step 中确认裁剪未发生（fixture 小 prompt 不会 drop）→ 仍通过。

## §11 边界清单 1:1（KPI）

### A. estimate_tokens (Unit A)
- A1 `estimate_tokens("")` → `1`（公式 0//4 + 1）
- A2 `estimate_tokens("a"*4)` → `2`（4//4 + 1）
- A3 `estimate_tokens("中文测试")` → `4`（12 bytes UTF-8 字面长度——注意：用 `len(str)` 即字符数，不是 bytes；4 chars → 4//4 + 1 = 2，**pin 字符数 not bytes**）—— 字面更新：→ `2`
- A4 函数纯 — 同输入同输出，无 IO 无 env 读
- A5 输入 `None` → AttributeError（不防御，让 caller 错误传参快速失败，PRINCIPLE 1）

### B. context_window_for / budget_for_retrieval (Unit B)
- B1 `context_window_for("openai", "gpt-4o")` → `128000`
- B2 `context_window_for("anthropic", "claude-sonnet-4-6")` → `200000`
- B3 `context_window_for("ollama", "qwen2.5:7b")` → `8192`（"*" 通配）
- B4 `context_window_for("ollama", "随便写")` → `8192`（不 warn）
- B5 `context_window_for("openai", "gpt-5-unknown")` → `8192` + stderr 一次 `mneme: unknown context window for openai/gpt-5-unknown, falling back to 8192 tokens`
- B6 同 (provider, model) 再 warn 一次 → 不输出第二次
- B7 yaml 缺 `context_windows:` 段 → 所有云模型 fallback 8192 + stderr 一次 `mneme: pricing.yaml missing context_windows section, falling back to 8192 tokens`
- B8 `budget_for_retrieval("openai", "gpt-4o")` → `128000 - max(1024, 32000) - 1024 = 94976`
- B9 `budget_for_retrieval("ollama", "qwen2.5:7b")` → `8192 - max(1024, 2048) - 1024 = 5120`
- B10 env `MNEME_CONTEXT_BUDGET_RATIO=0.5` 下 `budget_for_retrieval("openai", "gpt-4o")` → `128000 - max(1024, 64000) - 1024 = 62976`
- B11 env `MNEME_CONTEXT_BUDGET_RATIO=abc` → silent fallback 0.25 + stderr `mneme: invalid MNEME_CONTEXT_BUDGET_RATIO=abc, falling back to 0.25`
- B12 env `MNEME_CONTEXT_BUDGET_RATIO=0.0` → silent fallback 0.25 (边界开区间)
- B13 env `MNEME_CONTEXT_BUDGET_RATIO=1.5` → silent fallback 0.25
- B14 pure: B1-B10 不写文件、不调网络

### C. assemble_prompt (Unit C)
- C1 全部入 budget → `(prefix, suffix, meta)`，`meta.dropped_slice_ids == []`，`meta.kept_slice_ids == [s.id for s in slices]`
- C2 入 budget 时 `meta.original_slice_count == len(slices)`
- C3 末位低分 slice drop 1 个后入 budget → `meta.dropped_slice_ids == [slices[-1].id]`，kept 是前 n-1
- C4 drop 多个 slice 后入 budget → dropped_slice_ids 顺序 = 末→次末→...（drop 发生顺序）
- C5 slices=[]，prefix+user_text 入 budget → 直接返回，meta.dropped_slice_ids == []
- C6 slices=[]，prefix+user_text 超 budget → raise `PromptTooBig`，字面 `f"prompt exceeds budget after dropping all 0 retrieved slices: estimated={t} budget={budget}"`（n=0 同适用）
- C7 slices 全 drop 完仍超 budget → raise `PromptTooBig`，n=原始 slice 数
- C8 budget=0 → C6/C7 同行为（raise）
- C9 prefix 不被改变（出参 prefix is 入参 prefix string，identity 不要求但 equality 要求）
